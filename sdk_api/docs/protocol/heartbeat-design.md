# 心跳机制设计文档

本文档描述 Odin 设备与上位机之间的心跳连接管理机制，供上下位机开发人员共同参考。

---

## 1. 设计背景

当前 Odin 协议中，上位机通过 UDP 广播发现设备后直接建立 TCP 命令连接。存在以下问题：

- **无连接状态感知**：设备仅在 TCP `recv()` 返回错误时才知道上位机断开，无法主动检测上位机存活
- **无热插拔支持**：上位机无法周期性确认设备是否在线，设备掉电或网线断开后感知延迟大
- **无设备独占**：多个上位机可同时发现并尝试连接同一设备，缺少互斥机制

心跳机制通过独立的 TCP 通道实现上位机与设备之间的周期性存活确认，解决上述问题。

## 2. 端口规划

| 端口 | 协议 | 用途 |
|------|------|------|
| 60001 | UDP | 设备广播发现（DeviceQuery） |
| 60001 | TCP | 命令控制通道 |
| **60002** | **TCP** | **心跳通道（新增）** |

心跳通道使用独立端口，与命令通道解耦，确保心跳超时判定不受命令处理延迟影响。

## 3. 连接生命周期

### 3.1 建立流程

```
Host                                    Device
 │                                        │
 │─── UDP DeviceQuery (60001) ──────────>│  ① 广播发现
 │<── UDP DeviceQuery ACK ───────────────│
 │                                        │
 │─── TCP connect (60002) ──────────────>│  ② 建立心跳通道
 │─── 0x07 Heartbeat REQ ──────────────>│  ③ 首次心跳（含 interval）
 │<── 0x07 Heartbeat ACK ───────────────│     设备回传状态
 │                                        │
 │                              设备进入"已占用"状态
 │                              停止响应 UDP DeviceQuery
 │                                        │
 │─── TCP connect (60001) ──────────────>│  ④ 建立命令通道
 │─── SetMode / ChannelConfig ─────────>│  ⑤ 正常业务指令
 │                                        │
 │─── Heartbeat REQ (周期) ────────────>│  ⑥ 持续心跳
 │<── Heartbeat ACK ─────────────────────│
 │    ...                                 │
```

**关键约束**：
- 心跳通道 **必须在命令通道之前建立**
- 设备在收到首次心跳后即进入"已占用"状态
- 命令通道建立前，设备不接受任何控制指令

### 3.2 正常运行

```
Host                                    Device
 │                                        │
 │─── Heartbeat REQ ───────────────────>│  每 interval (建议 1000ms)
 │<── Heartbeat ACK ─────────────────────│  含设备实时状态
 │                                        │
 │    （并行进行命令/数据交互）               │
```

### 3.3 断开与超时

```
场景 A: 上位机主动断开
─────────────────────────
Host 关闭心跳 TCP 连接 → Device 检测到 FIN
  → Device 执行全重置（见 §4.2）
  → Device 恢复响应 UDP DeviceQuery

场景 B: 心跳超时（网络异常/上位机崩溃）
──────────────────────────────────────
Device 连续 3 个心跳周期未收到 REQ
  → Device 执行全重置（见 §4.2）
  → Device 恢复响应 UDP DeviceQuery

场景 C: 上位机检测设备掉线
──────────────────────────
Host 发送 Heartbeat REQ 后 TCP 写入失败或超时无 ACK
  → Host 判定设备离线
  → Host 关闭所有连接，回到 UDP 发现阶段
```

## 4. 心跳指令定义

### 4.1 0x07 Heartbeat

复用现有控制协议帧格式（见 PROTOCOL.md §1.1），通过独立的心跳 TCP 端口 60002 传输。

**REQ** (Host → Device, TCP 60002)

| 名称 | 类型 | 描述 |
|------|------|------|
| heartbeat_interval_ms | uint16_t | Host 心跳发送间隔(ms)，建议值 1000 |

**ACK** (Device → Host, TCP 60002)

| 名称 | 类型 | 描述 |
|------|------|------|
| ret_code | uint8_t | 返回码 (0=成功) |
| uptime_s | uint32_t | 设备运行时间(秒) |

**说明**：
- 首次心跳中的 `heartbeat_interval_ms` 用于设备计算超时阈值
- 后续心跳中 `heartbeat_interval_ms` 可保持相同值，若 Host 动态调整间隔，设备跟随更新
- 帧头 `cmd_id = 0x07`，其余字段（sof、version、seq、crc 等）遵循现有帧格式

### 4.2 超时策略

| 参数 | 值 | 说明 |
|------|------|------|
| 心跳间隔 | 由 Host 指定（建议 1000ms） | 首次 REQ 中的 `heartbeat_interval_ms` |
| 超时判定 | 3 × heartbeat_interval_ms | 连续 3 个周期未收到心跳 |
| 默认超时 | 3000ms | 当 interval = 1000ms 时 |

**设备端超时后执行全重置**：
1. 停止所有数据通道推流
2. 关闭所有 TCP 数据连接
3. 主动关闭命令 TCP 连接（60001）
4. 重置所有通道订阅配置
5. 关闭心跳 TCP 连接（60002）
6. 恢复响应 UDP DeviceQuery 广播

## 5. 设备独占机制

### 5.1 规则

- 心跳 TCP 连接建立后，设备**静默忽略** UDP DeviceQuery 广播（不回复 ACK）
- **命令通道门控**：心跳未建立时，设备不接受 TCP 命令连接（command_loop 阻塞等待心跳）
- 效果：已被占用的设备对其他上位机不可见；未建立心跳时上位机无法发送任何业务指令
- 心跳断开或超时 → 全重置后恢复 DeviceQuery 响应，设备重新可被发现

### 5.2 状态转换

```
          UDP DeviceQuery
          ┌──────────┐
          │          │
          ▼          │ 响应 ACK
    ┌──────────┐     │
    │  空闲     │─────┘
    │ (可发现) │
    └────┬─────┘
         │ 心跳 TCP 连接建立
         ▼
    ┌──────────┐
    │  已占用   │──── 忽略 UDP DeviceQuery
    │(不可发现) │
    └────┬─────┘
         │ 心跳断开 / 超时
         ▼
    ┌──────────┐
    │  空闲     │──── 全重置，恢复响应
    │ (可发现) │
    └──────────┘
```

## 6. Host 端实现要点

### 6.1 连接顺序

1. UDP 广播 DeviceQuery → 获取设备 IP
2. TCP 连接心跳端口 (60002)
3. 发送首次 Heartbeat REQ（含 interval）
4. 收到 ACK 确认设备就绪
5. TCP 连接命令端口 (60001)
6. 发送 SetMode / ChannelConfig 等业务指令

### 6.2 心跳维护

- 启动周期定时器，按 `heartbeat_interval_ms` 发送 Heartbeat REQ
- 每次收到 ACK 后可检查 `work_mode`、`active_mask`、`error_code` 更新 UI/状态
- 发送失败或无 ACK 超时 → 进入重连流程

### 6.3 重连策略

```
检测到设备离线（心跳发送失败 / ACK 超时）
  → 关闭所有 TCP 连接（心跳 + 命令 + 数据）
  → 回到 UDP DeviceQuery 发现阶段
  → 周期广播发现（建议 1Hz）
  → 发现设备后重新执行完整连接流程
```

### 6.4 主动断开

上位机主动断开时，按以下顺序关闭：
1. 发送 SetMode(Standby) 停止推流（可选）
2. 关闭命令 TCP 连接
3. 关闭心跳 TCP 连接
4. 关闭所有数据接收端口

## 7. 与现有指令的交互

| 场景 | 行为 |
|------|------|
| 心跳未建立时收到 TCP 命令连接 | 设备接受连接但建议 Host 先建立心跳 |
| 心跳超时触发全重置 | 等价于现有的 `on_client_disconnect` 行为 |
| SetMode(Standby) | 不影响心跳，心跳持续运行 |
| SetMode(Normal) | 不影响心跳，心跳持续运行 |
| 命令 TCP 断开但心跳仍在 | 停流+重置通道配置，但设备保持"已占用"状态 |
| 心跳 TCP 断开 | 触发全重置（含断开命令 TCP） |

## 8. 指令 ID 汇总

| cmd_id | 指令 | 传输 | 端口 |
|--------|------|------|------|
| 0x01 | DeviceQuery | UDP | 60001 |
| 0x02 | VersionQuery | TCP | 60001 |
| 0x03 | GetSensorCapability | TCP | 60001 |
| 0x04 | SetMode | TCP | 60001 |
| 0x05 | SetLiDARMode | TCP | 60001 |
| 0x06 | ChannelConfig | TCP | 60001 |
| **0x07** | **Heartbeat** | **TCP** | **60002** |
